# DEV door for DEV passes Implementation Plan (shyden-labs/shydesk#302)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan
> task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** ShyDesk's dev Worker answers only requests carrying a valid DEV pass, except `/health`
and the public embed scripts, while the dev product pages keep sending support requests.

**Architecture:** repo-template's `door.ts`, `pass.ts` and `form.ts` are copied into
`src/dev-door/` at shyden-labs/repo-template@449e1c612e9671a0eaaffee33dd4330fe0f306e3, minus the
door secret (the door forwards in-process). `src/index.ts`'s `fetch` wraps `app.fetch` in the door
when `DEV_PASS_KEYS` is set (env.dev only). `public/embed.js` fetches an embed pass from its page's
own door when its HOST is the dev host and sends it as `X-Dev-Pass`.

**Tech Stack:** Hono Worker, Web Crypto Ed25519, Vitest (unit, `--config vitest.unit.config.ts`).

**Spec:** `docs/superpowers/specs/2026-11-26-dev-door-design.md`.

## Review Focus

1. A pass sent to a staff page by cookie AND a CF_Authorization Access cookie: both must reach
   the handlers; the door strips only `__Host-devpass`. Test in Task 2.
2. An OPTIONS preflight from an origin the door lists but the product does not allow: the door
   answers 204, then ShyDesk's own origin check refuses the real request. Test in Task 2.
3. `embed.js` on a live page (HOST not the dev host) must never call `/__devpass/embed`. Test in Task 3.
4. A second 401 after a fresh embed pass shows the failure line; no third request. Task 3.
5. `DEV_PASS_KEYS` set but malformed JSON: the Worker refuses every gated request with 500 naming
   the variable, never opens the gate. Task 2.
